# Kubernetes bootstrap: secrets and deployment handoff

The [operator manifests](../deploy/mariadb/operator/) include the current runtime
grants, including schema-11 Discover. CI compares every runtime Grant against the
startup permission contract, including database-wide SELECT, and rejects missing,
duplicate, overbroad or incorrectly targeted grants. This is repository validation,
not an exercised cluster deployment. See the [rollout guide](deployment.md#production-style-staging-rollout)
and [operator prerequisites](persistence.md#standalone-operator-example-not-deployed).

Secret provisioning and private database setup do not depend on a public Gateway
address. Finish the existing nginx Gateway test before attaching Ticketopia.
cert-manager's ACME staging certificates are not publicly trusted; Gateway
`ResolvedRefs=True` is not proof of working TLS, and `Accepted=True` is not proof
of programming or external reachability.

## Required secrets

All application/database Secrets below belong in the **`ticketopia` namespace**.
Create them through the existing secret manager if one is available; otherwise
use the fresh-install commands below. Never commit populated Secret YAML, put
credentials in CLI literal arguments, paste them into an agent chat, or log them.
Kubernetes Secrets are base64-encoded, not inherently encrypted: restrict RBAC and
configure encryption at rest for the cluster.

| Secret | Key / type | Source and consumer |
| --- | --- | --- |
| `ticketopia-db-root` | `password` | Unique random admin password; MariaDB/operator only |
| `ticketopia-db-runtime` | `password` | Different random password; runtime User and app pods |
| `ticketopia-db-migration` | `password` | Different random password; migration User and Job only |
| `ticketopia-provider` | `ticketmaster-key` | Your Ticketmaster Discovery API key; app pods only |
| `ghcr` | `.dockerconfigjson`, `kubernetes.io/dockerconfigjson` | GHCR account plus pull-only classic PAT with `read:packages` and access to the private package; app and Job |
| `ticketopia-db-ca-bundle` | `ca.crt` | Generated by mariadb-operator; do not create a competing Secret or substitute the public Gateway certificate |

Keep the existing Cloudflare DNS token and Gateway TLS Secret in their current
issuer/Gateway namespaces. They are unrelated to the database credentials. The
base application manifest leaves Google accounts disabled. If enabling them later,
use a separate auth Secret/ConfigMap and a real HTTPS origin as described in
[Google account deployment](deployment.md#optional-google-accounts).

## Fresh-install provisioning commands

These commands **change the selected cluster**; review and authorize them first.
Use a shell without command tracing (`set -x`). Confirm the context, namespace,
Secret names, and whether an existing database/PVC or external secret controller
already owns them. **Do not regenerate or overwrite existing credentials** just to
rerun bootstrap. Existing installs must reuse their secret manager/credential
source and follow a separately approved rotation plan if credentials change.

Use Bash for this command block. Requires `kubectl`, OpenSSL and Docker for the
isolated GHCR login. The later manifest filter uses **Mike Farah's `yq` v4**, not
the unrelated Python utility.
Replace nonsecret placeholders below locally. Obtain the Ticketmaster key and
GHCR PAT through your password manager into separate owner-only files, with no
trailing newline. Do not ask the agent to print or handle their values in chat.

```sh
set -euo pipefail
CONTEXT=YOUR_CONFIRMED_KUBERNETES_CONTEXT
GHCR_USER=YOUR_GITHUB_USERNAME
TICKETMASTER_KEY_FILE=/PRIVATE/PATH/ticketmaster-key
GHCR_PAT_FILE=/PRIVATE/PATH/ghcr-pull-token

kubectl --context "$CONTEXT" cluster-info
kubectl --context "$CONTEXT" create namespace ticketopia --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" apply --server-side --field-manager=ticketopia-bootstrap -f -

# Fresh installs only. Inspect names, not Secret values; stop on existing
# credentials/PVCs or failed API queries instead of guessing a rotation plan.
for name in ticketopia-db-root ticketopia-db-runtime ticketopia-db-migration ticketopia-provider ghcr; do
  existing=$(kubectl --context "$CONTEXT" -n ticketopia get secret "$name" --ignore-not-found -o name)
  if [ -n "$existing" ]; then
    printf 'Secret %s already exists; stop and reuse its managed credential source.\n' "$name" >&2
    exit 1
  fi
done
existing_pvcs=$(kubectl --context "$CONTEXT" -n ticketopia get pvc -o name)
if [ -n "$existing_pvcs" ]; then
  printf 'Existing PVCs found; stop and review database/credential ownership.\n' >&2
  exit 1
fi
test -r "$TICKETMASTER_KEY_FILE"
test -r "$GHCR_PAT_FILE"
test -s "$TICKETMASTER_KEY_FILE"
test -s "$GHCR_PAT_FILE"

umask 077
SECRET_DIR=$(mktemp -d "${TMPDIR:-/tmp}/ticketopia-secrets.XXXXXX")
openssl rand -hex 32 | tr -d '\n' > "$SECRET_DIR/root-password"
openssl rand -hex 32 | tr -d '\n' > "$SECRET_DIR/runtime-password"
openssl rand -hex 32 | tr -d '\n' > "$SECRET_DIR/migration-password"

kubectl --context "$CONTEXT" -n ticketopia create secret generic ticketopia-db-root \
  --from-file=password="$SECRET_DIR/root-password" --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" -n ticketopia apply --server-side --field-manager=ticketopia-secrets -f -
kubectl --context "$CONTEXT" -n ticketopia create secret generic ticketopia-db-runtime \
  --from-file=password="$SECRET_DIR/runtime-password" --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" -n ticketopia apply --server-side --field-manager=ticketopia-secrets -f -
kubectl --context "$CONTEXT" -n ticketopia create secret generic ticketopia-db-migration \
  --from-file=password="$SECRET_DIR/migration-password" --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" -n ticketopia apply --server-side --field-manager=ticketopia-secrets -f -
kubectl --context "$CONTEXT" -n ticketopia create secret generic ticketopia-provider \
  --from-file=ticketmaster-key="$TICKETMASTER_KEY_FILE" --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" -n ticketopia apply --server-side --field-manager=ticketopia-secrets -f -

# Isolate Docker credentials from the normal login/configuration. The PAT is
# read from stdin, not placed in command arguments or environment variables.
mkdir "$SECRET_DIR/docker"
docker --config "$SECRET_DIR/docker" login ghcr.io --username "$GHCR_USER" \
  --password-stdin < "$GHCR_PAT_FILE"
kubectl --context "$CONTEXT" -n ticketopia create secret generic ghcr \
  --type=kubernetes.io/dockerconfigjson \
  --from-file=.dockerconfigjson="$SECRET_DIR/docker/config.json" --dry-run=client -o yaml |
  kubectl --context "$CONTEXT" -n ticketopia apply --server-side --field-manager=ticketopia-secrets -f -
```

The YAML pipelines carry secret data: do not capture them in logs, add `tee`, or
run a client dry-run unpiped in a recorded terminal. Server-side apply avoids the
client-side last-applied annotation containing another copy of the secret. Do not
use `--force-conflicts`; investigate field ownership rather than overwriting a
secret controller. Store the generated passwords in your secret manager before
removing only these known temporary files. Keep private files outside Git, and
verify Secret **names, types and key names**, not values.

### Apply infrastructure without overwriting secrets

Install/review the pinned operator and CRDs first and confirm storage and amd64
scheduling requirements. Do **not** apply `database.yaml` unfiltered: its example
Secret values would overwrite real credentials. Keep that source file unchanged
and exclude all Secret documents when provisioning them separately:

```sh
yq eval 'select(.kind != "Secret")' deploy/mariadb/operator/database.yaml |
  kubectl --context "$CONTEXT" apply --server-side --field-manager=ticketopia-bootstrap -f -
```

Wait for MariaDB, Database, both Users, and the migration Grant to be `Ready`, and
for `ticketopia-db-ca-bundle` to contain `ca.crt`. Table-specific runtime Grants
cannot succeed before migrations create their tables: **do not wait for all
Grants before running the migration Job**. Run a uniquely named migration Job
using the same pinned image digest as the app. If migration fails, stop and inspect
the sanitized logs/dirty-schema recovery procedure; do not retry blindly. After
Job success, wait for **all** runtime Grants, then deploy the app and verify
`/healthz`, `/readyz` and rollout status. App startup additionally checks required
writes without changing data. Migrations never grant privileges, and `make db-setup`
must not be pointed at this cluster.

## Copy-paste prompt for your cluster agent

```text
Help me continue my existing Kubernetes setup and prepare Ticketopia safely.
Read this repository's AGENTS.md, docs/kubernetes-bootstrap.md,
docs/persistence.md and docs/deployment.md, plus deploy/mariadb/operator/.

My reported progress (verify live status; do not redo completed setup):
- [x] Cilium 1.20.2 running
- [x] Gateway API enabled
- [x] GatewayClass accepted
- [x] cert-manager installed
- [x] Cloudflare DNS-01 staging succeeded
- [x] Gateway accepted
- [x] Gateway TLS Secret reference resolved
- [ ] Gateway external address configured
- [ ] Gateway programmed successfully
- [ ] nginx HTTPRoute attached and verified
- [ ] Cloudflare wildcard DNS configured

Start read-only. Confirm the intended kubeconfig context, Gateway/namespace,
domain, storage class, amd64 capacity and existing secret-management tooling.
Do not dump Secret data, tokens, kubeconfig credentials or populated YAML.
Before any cluster or Cloudflare changes, summarize the exact proposed changes
and obtain approval. Never rotate existing credentials, delete PVCs, reinstall
Cilium/cert-manager, or replace working Gateway/DNS-01 resources without approval.

1. Inspect Gateway conditions and its generated Service. Determine the actual
   environment (managed cloud, bare metal or other) and existing Cilium IPAM/
   L2/BGP/cloud load-balancer configuration. Ask for the approved address pool,
   network/advertisement mode and external routing details when unresolved.
   Do not invent an address or use status patches as a reachability fix. Address
   assignment alone is insufficient: verify traffic can reach the Gateway.
2. Propose the smallest configuration to establish a routable external address
   and Programmed=True. Verify nginx HTTPRoute Accepted/ResolvedRefs and actual
   HTTP/HTTPS requests for its hostname before adding Ticketopia. Check Cloudflare
   wildcard DNS, apex needs and proxy mode deliberately; distinguish origin from
   Cloudflare edge results. ACME staging certificates are not publicly trusted;
   plan an approved production issuer/certificate step before production TLS.
3. Provision namespace-local Ticketopia secrets using the existing secret manager
   or the fresh-install file/stdin commands in docs/kubernetes-bootstrap.md:
   ticketopia-db-root/password, ticketopia-db-runtime/password,
   ticketopia-db-migration/password, ticketopia-provider/ticketmaster-key and
   ghcr/.dockerconfigjson. Generate three distinct strong database passwords only
   for a genuinely fresh database. Request private local file paths, not secret
   values in chat. Use a pull-only GHCR PAT with read:packages and package access.
   Never copy a Cloudflare token or Gateway TLS private key into the app namespace.
   Let mariadb-operator generate ticketopia-db-ca-bundle/ca.crt.
4. Propose database deployment with Secret placeholder documents filtered out.
   Verify operator/CRD compatibility and storage; wait for database/users/migration
   grants, run a uniquely named migration Job, then wait for all runtime grants.
   Deploy the app privately and verify rollout, /healthz and /readyz. Pin the Job
   and app to the same published image digest. Do not run local
   make db-setup or migrations from every app pod. Stop on migration failure.
5. Only after the nginx test and private database/app checks pass, propose an
   HTTPRoute to ticketopia Service port 80 using the existing Gateway, correct
   namespaces/listener/hostname and allowedRoutes. Do not expose MariaDB publicly.
   Leave Google auth disabled unless requested; enabling it needs a real HTTPS
   origin and separately provisioned Google OAuth credentials/callback.

Deliver an ordered plan, nonsecret manifests/commands and verification for each
stage. Mark checklist items complete only from observed conditions AND successful
traffic tests. Report remaining blockers and unverified production concerns;
do not claim backups, HA or production-trusted TLS merely because pods are Ready.
```
